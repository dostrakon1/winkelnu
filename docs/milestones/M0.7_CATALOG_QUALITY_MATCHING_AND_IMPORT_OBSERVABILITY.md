# M0.7 — Catalog Quality, Matching & Import Observability

Status: Completed  
Date: 2026-09-03

## Goal

Make affiliate feed ingestion safe, observable and reviewable before connecting real partner feeds.

## Delivered

- Explicit product matching decisions with method, confidence, reasons and review requirement.
- Import-run lifecycle and counters.
- Separate rejected-record storage contract.
- Pending matching-review queue contract.
- Duplicate merchant-product protection inside a run.
- Duplicate canonical-target detection inside a run.
- Stale-offer deactivation after successful full feed traversal.
- Failed imports do not execute stale-offer cleanup.
- In-memory implementation for the synthetic vertical slice.
- PostgreSQL/Supabase migration for rejects, review queue and additional run metrics.
- Architecture policy documenting quality and failure semantics.

## Acceptance criteria

- [x] Every import begins with a traceable run record.
- [x] Successful and failed imports have explicit final states.
- [x] Validation failures cannot enter the public catalog.
- [x] Rejected source records remain diagnosable.
- [x] Ambiguous matching decisions are reviewable rather than silently merged.
- [x] Duplicate merchant product IDs in one run are rejected deterministically.
- [x] Multiple records targeting one canonical product are surfaced for review.
- [x] Missing offers are deactivated only after a complete successful feed traversal.
- [x] A failed source retrieval cannot mass-deactivate a merchant's offers.
- [x] Persistence schema can represent import metrics, rejects and matching reviews.

## Important boundary

M0.7 does not implement an internal operations UI yet. It defines the data, contracts and behaviour that such a UI will consume later.

M0.8 — Supabase Persistence Adapter & Repository Integration.
