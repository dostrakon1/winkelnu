# M0.13 — Search & Filter Query Architecture

Status: COMPLETE (repository-side)
Date: 2026-09-03

## Goal

Introduce a controlled public search/filter contract without creating uncontrolled indexable URL combinations or coupling Next.js routes directly to persistence-specific query APIs.

## Implemented

- Central `CatalogSearchQuery` contract.
- Defensive query parser for public URL input.
- Search term normalization and length bounding.
- Category, brand, minimum/maximum total-price and stock filters.
- Sorting by relevance, total price ascending/descending and title.
- Bounded page and page-size input.
- Search service above `CatalogReadRepository`.
- Public `/zoeken` route with shareable GET parameters.
- Homepage search entry point.
- Filter-preserving previous/next pagination.
- Search result URLs are always `noindex,follow`.
- Canonical search URL is `/zoeken`.
- Search/filter combinations are intentionally excluded from the sitemap.
- Automated parser and search behavior tests.

## SEO policy

Search and arbitrary filter combinations are discovery tools, not durable landing pages. Therefore:

- `/zoeken` and all parameter combinations are `noindex,follow`;
- crawlers may follow product/category links from result pages;
- search parameter URLs are never added to the sitemap;
- durable category and canonical product URLs remain the indexable catalog surface;
- future curated landing pages must be explicit first-class routes rather than accidental query combinations.

## Price semantics

Price filters and price sorting operate on the best known total offer amount (product price plus known shipping cost), not only the merchant's displayed item price.

## Current scale boundary

The application contract is deliberately persistence-independent. During the current small/synthetic phase, `CatalogService.searchProducts()` enriches a bounded candidate set (maximum 240 products) and applies filtering in the application layer.

This is not the intended large-catalog execution strategy. A later scale milestone should push text search, filter predicates, ranking and cursor pagination into PostgreSQL/search infrastructure while preserving the same public application contract.

## Safety properties

- malformed public parameters cannot create unbounded page sizes;
- min/max price values are normalized and reversed when supplied backwards;
- unsupported sort modes fall back to relevance;
- empty/malformed numeric filters are ignored rather than trusted;
- only products with an active best offer enter current search results;
- stock-only filtering checks offer availability explicitly.

## Acceptance criteria

M0.13 is repository-complete when:

1. search/filter parameters have a central parser;
2. routes do not query Supabase directly;
3. filtering/sorting behavior is covered by automated tests;
4. arbitrary search/filter combinations are non-indexable;
5. result pagination preserves the active query;
6. durable sitemap behavior from M0.12 remains unchanged.

Live Supabase-scale query optimization is intentionally deferred until real catalog volume exists.
