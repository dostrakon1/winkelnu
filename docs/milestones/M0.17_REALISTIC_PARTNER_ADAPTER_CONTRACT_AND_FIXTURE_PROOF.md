# M0.17 — Realistic Partner Adapter Contract & Fixture Proof

Status: Completed repository-side
Date: 2026-09-03

## Goal

Prove that a provider-like external feed can be resolved through the M0.15/M0.16 integration registry, converted through a concrete adapter, paginated, normalized and imported without leaking provider-specific concepts into the catalog/domain layers.

## Delivered

- realistic provider fixture with non-Winkelnu field names;
- cursor-based pagination across two pages;
- `RealisticPartnerFixtureAdapter` mapping into `FeedCandidate`;
- stock-state normalization;
- product/tracking URL mapping;
- previous-price and shipping-cost mapping;
- malformed fixture record for negative-path validation;
- unknown-cursor transport failure;
- end-to-end registry → resolver → adapter-registry → import proof;
- import bootstrap ordering corrected for relational persistence;
- automated tests for mapping, pagination, rejects and fail-closed cursor behavior;
- architecture document `REALISTIC_PARTNER_ADAPTER_CONTRACT.md`.

## Important boundary

The adapter translates external data. It does not decide catalog validity. Existing domain validation remains the authority for rejecting malformed normalized candidates.

## External gate

No real network credential or live partner endpoint is used in M0.17. The milestone proves the contract before a production partner is connected.

## Next logical milestone

**M0.18 — First Real Partner Integration Readiness**: choose one actual affiliate/network integration target, define its authentication/feed transport contract, environment-variable contract, rate-limit/retry policy and sandbox/read-only verification path before enabling production imports.
