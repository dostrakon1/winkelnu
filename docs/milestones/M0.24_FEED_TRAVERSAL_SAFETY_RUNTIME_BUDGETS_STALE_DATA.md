# M0.24 — Feed Traversal Safety, Runtime Budgets & Stale Data Policy

Status: repository-side implemented; CI verification pending.

## Delivered
- repeated-cursor detection;
- maximum page budget per import;
- wall-clock runtime budget independent from business timestamps;
- traversal safety failures recorded as failed import runs;
- stale-offer cleanup remains skipped on failed traversal;
- explicit `fresh | stale | expired` offer classification;
- baseline freshness thresholds of 24h stale / 72h expiry;
- expired offers excluded from public CatalogService ranking/detail/search;
- stale offers retained with freshness metadata for UI disclosure;
- focused tests for cursor loops, page budgets, runtime budgets and storefront freshness behavior.

## Default safety envelope
- 10,000 pages maximum per import;
- 30 minutes application traversal budget;
- hard configuration cap: 100,000 pages / 6 hours;
- any repeated non-empty cursor fails closed.

## Freshness rationale
`lastSeenAt` is the verification clock. `sourceUpdatedAt` can remain old even when a current feed confirms the same price, so it is not used as the storefront freshness clock.

Temporary partner outages therefore degrade offers from fresh to stale before eventual expiry rather than immediately wiping the merchant from the storefront.
