# M0.8 — Supabase Persistence Adapter & Repository Integration

Status: repository implementation complete; live project activation pending external Supabase access.

Date: 2026-09-03

## Objective

Replace the temporary persistence assumption with a real PostgreSQL/Supabase adapter without coupling the application/domain layers to Supabase.

## Delivered

- Added `@supabase/supabase-js` server dependency.
- Raised the runtime/CI baseline to Node 22.
- Added a server-only Supabase client requiring `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`.
- Added `SupabaseCatalogRepository` implementing the existing catalog read/write ports.
- Added a persistence factory controlled by `CATALOG_PERSISTENCE=memory|supabase`.
- Routed the synthetic catalog through that factory so the adapter seam is exercised by the application structure.
- Added migration `0003_domain_external_keys.sql` to keep stable Winkelnu domain IDs separate from relational UUID primary keys.
- Added environment and activation documentation.

## Persistence mapping

Application identity examples:

- `merchant:synthetic-demo-store`
- `category:audio`
- `product:<gtin>`
- `offer:<merchant>:<merchant-product>`
- `import:<source>:<timestamp>`

These are stored as `external_key`. PostgreSQL UUID columns remain the internal relational primary/foreign keys.

## Repository coverage

The Supabase adapter now covers:

- merchant upsert/read;
- product upsert/read/list;
- offer upsert/read/deactivation;
- category reads;
- import-run create/update/list;
- rejected-record persistence/read;
- match-review persistence/read.

## Security boundary

The catalog adapter uses the Supabase service-role key and is therefore server-only. The service-role key must never be exposed to browser code or `NEXT_PUBLIC_` variables.

No public Supabase client is introduced in M0.8.
