# M0.20 — Import Scheduling, Concurrency Lease & Failure Recovery

Status: repository-side implemented; final CI verification pending.

## Delivered
- persistence-independent orchestration domain state;
- `ImportOrchestrationRepository` port;
- `ImportOrchestrationService.runExclusive()`;
- atomic per-feed lease acquisition;
- due-time enforcement through `next_run_at`;
- stale lease takeover after expiry;
- token-protected success/failure completion;
- exponential retry backoff with a 6-hour cap;
- success cadence bootstrap (default one hour);
- in-memory orchestration repository;
- Supabase orchestration repository;
- migration `0006_import_orchestration.sql`;
- database contract/smoke-test expansion;
- automated concurrency/recovery tests;
- M0.19 lint regression fixed with real `FeedCandidate` typing.

## Safety guarantees
- two workers cannot concurrently own the same feed lease;
- premature scheduler triggers cannot bypass `next_run_at`;
- a crashed worker releases ownership implicitly through lease expiry;
- stale workers cannot complete after a new lease token has taken ownership;
- repeated failures back off instead of hammering a partner endpoint;
- successful recovery resets failure state;
- storefront traffic is not used as an import scheduler.

## Deliberate boundary
M0.20 does not pick Vercel Cron, a queue, GitHub Actions or a dedicated worker as the final runtime. Those are delivery mechanisms above the orchestration contract.

Long-running imports above the lease duration will require heartbeat/renewal before production scale.
