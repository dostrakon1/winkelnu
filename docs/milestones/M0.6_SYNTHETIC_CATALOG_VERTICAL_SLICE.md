# M0.6 — Synthetic Catalog Vertical Slice

Status: Completed
Date: 2026-09-03

## Goal

Prove the core Winkelnu architecture end-to-end before connecting a real affiliate partner or production database.

## Implemented path

Synthetic merchant feed
→ FeedAdapter
→ domain validation
→ import use case
→ deterministic canonical product identity
→ merchant offer creation
→ Catalog repository ports
→ in-memory persistence adapter
→ storefront product listing
→ canonical product detail route

## Why in-memory persistence is correct for this milestone

A production Supabase project has not yet been connected. The vertical slice therefore uses `InMemoryCatalogRepository`, which implements the same application repository interfaces intended for the later Postgres/Supabase adapter.

This prevents the storefront and import logic from becoming coupled to a temporary storage implementation. When Supabase is connected, persistence can be replaced at the infrastructure boundary without rewriting the catalog domain or UI flow.

## Synthetic data

The demo merchant intentionally uses `.invalid` URLs and clearly synthetic products. These records must never be treated as production affiliate offers.

The feed currently proves:
- multiple products from one merchant;
- strong product identity using GTIN when available;
- merchant-specific offer identity;
- monetary values represented as decimal strings;
- source category mapping into Winkelnu categories;
- affiliate URL separation from canonical product identity;
- import rejection reporting;
- public rendering from imported catalog state.

## Acceptance criteria

- [x] Feed source is accessed through a `FeedAdapter`.
- [x] Feed candidates are validated before persistence.
- [x] Canonical product records are not merchant records.
- [x] Offers remain merchant-specific.
- [x] Storefront reads through catalog repository contracts.
- [x] Product pages use stable Winkelnu slugs rather than merchant URLs.
- [x] Affiliate CTA clearly says `Bekijk aanbieding`.
- [x] Storefront states that Winkelnu is not the seller.
- [x] Persistence implementation can later be swapped for Supabase/Postgres.

## Known deliberate limitation

The product matcher in M0.6 uses a deterministic strong-identifier strategy suitable for proving the architecture. Confidence scoring, conflicting identifiers, reversible merge decisions and operator review belong to a later catalog-quality milestone.
